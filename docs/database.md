# Схема базы данных и миграции

## Что хранится в PostgreSQL

Проект использует две предметные таблицы:

- `images` хранит готовые JPEG-изображения и их параметры;
- `tasks` хранит состояние асинхронной обработки.

Отдельная служебная таблица `schema_migrations` хранит версии уже выполненных SQL-миграций.

Связи выглядят так:

```text
tasks.source_image_id ──> images.id   # исходник задачи resize
tasks.result_image_id ──> images.id   # результат выполненной задачи
```

Для задачи загрузки исходником является файл в настроенной директории, поэтому используется
`tasks.source_path`. Для задачи изменения существующего изображения исходником является строка
в PostgreSQL, поэтому используется `tasks.source_image_id`.

## Таблица images

Поле `content BYTEA` содержит байты готового JPEG. Это сознательный выбор под формулировку ТЗ:
результат должен сохраняться в базе данных.

Остальные важные поля:

- `id UUID` — идентификатор, который генерирует Python;
- `original_filename` — исходное имя для метаданных;
- `media_type` — для данного ТЗ всегда `image/jpeg`;
- `width` и `height` — фактические размеры результата;
- `size_bytes` — фактический размер сохранённых байтов;
- `quality` — запрошенное качество JPEG либо `NULL`, если клиент его не передал;
- `created_at` и `updated_at` — время создания и последнего изменения.

Ограничения `CHECK` не позволяют сохранить отрицательные размеры, пустое содержимое,
неподдерживаемый media type или quality вне диапазона 1–100.

## Таблица tasks

`task_type` принимает два значения:

- `upload` — обработать файл из директории загрузок;
- `resize` — изменить существующее изображение из таблицы `images`.

`status` принимает значения:

```text
pending -> processing -> completed
                      \-> failed
```

Для `upload` должны быть заполнены `source_path` и `original_filename`. Для `resize`
должны быть заполнены `source_image_id`, `target_width` и `target_height`.
Эти правила контролируются самой базой.

При статусе `completed` обязательны `started_at`, `finished_at` и `result_image_id`.
При статусе `failed` обязательны временные метки и `error_message`.

## Как работает мигратор

Сначала заполните `POSTGRES_DSN` в локальном `.env`. Формат строки подключения:

```dotenv
POSTGRES_DSN=postgresql://postgres:postgres@localhost:5432/image_service
```

Без существующей базы `image_service` мигратор подключиться не сможет: он создаёт таблицы,
но не создаёт саму базу PostgreSQL.

Команда запуска:

```powershell
venv\Scripts\python.exe -m app.db.migrate up
```

Проверка состояния без изменения схемы:

```powershell
venv\Scripts\python.exe -m app.db.migrate status
```

Алгоритм команды `up`:

1. Загружает `POSTGRES_DSN` из `.env` и путь миграций из `config.cfg`.
2. Находит файлы вида `0001_name.sql` и сортирует их по имени.
3. Открывает одно соединение через `asyncpg.connect()`.
4. Берёт PostgreSQL advisory lock, чтобы два процесса не мигрировали одну базу одновременно.
5. Создаёт служебную таблицу `schema_migrations`, если её ещё нет.
6. Сверяет выполненные версии и SHA-256 checksum.
7. Выполняет каждую новую миграцию в отдельной транзакции.
8. В той же транзакции записывает её версию и checksum в `schema_migrations`.
9. Освобождает блокировку и закрывает соединение.

Если SQL завершится ошибкой, контекст `connection.transaction()` выполнит `ROLLBACK`.
Строка с версией также не сохранится, поэтому после исправления новой, ещё не применённой
миграции команду можно повторить.

## Почему используется одно соединение, а не pool

API и worker работают долго и обслуживают много одновременных операций, поэтому им нужен pool.
Мигратор — короткая последовательная команда. Ему достаточно одного соединения, и на этом же
соединении удерживается advisory lock.

## Правило неизменяемых миграций

После применения SQL-файл нельзя редактировать или удалять. Мигратор хранит его checksum и
остановится, если содержимое изменилось.

Любое следующее изменение оформляется новым файлом:

```text
0003_add_images_sha256.sql
0004_add_tasks_retry_count.sql
```

Миграции в этом проекте forward-only: вместо ручного отката старого файла создаётся новая
миграция, которая исправляет схему. Это сохраняет одинаковую и проверяемую историю на всех
окружениях.

## Где находятся файлы

```text
app/db/sql/schema.sql                  # служебная таблица версий
app/db/migrations/0001_create_images.sql
app/db/migrations/0002_create_tasks.sql
app/db/migrate.py                      # asyncpg migration runner
```
